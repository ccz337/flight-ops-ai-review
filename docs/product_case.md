# AI 产品案例：航司运行稳定性比较与可审计解释

## 1. 问题与用户

目标用户是需要在多个航班或航空公司之间选择的消费者。他们通常能看到价格和时刻，但不容易把历史取消、延误频率、准点表现和延误严重程度放到同一可比范围内理解。

本项目的产品任务是：在相同始发机场、目的地和日期范围内，输出可追溯的历史运行指标，并生成带证据引用和限制说明的消费者解释。

当前没有真实用户访谈或线上行为数据，因此这是待验证的产品假设，不把作品集原型包装成已验证业务需求。

## 2. MVP 范围

### 纳入

- `nycflights13 1.0.2` 中 2013 年从 EWR、JFK、LGA 出发的航班。
- 相同航线、相同日期范围下的航司比较。
- 计划航班量、取消率、有效到达样本、到达延误率、到达准点率、延误航班平均延误时长。
- 样本门禁、证据引用、限制披露、AI 失败降级与运行审计。

### 不纳入

- 实时或未来航班预测。
- 票价、服务、行李、航线便利性和安全评价。
- 未经用户研究与统计验证的综合稳定性分数。
- 天气、机场拥堵或航司责任的因果归因。

## 3. 核心产品决策

### 决策一：先固定可比条件，再比较航司

不同航线和时间段的运行难度可能不同。系统强制使用同一始发机场、目的地和日期范围，避免把航线或季节差异误写成航司差异。

### 决策二：分开展示指标，不制造单一赢家

到达准点率与到达延误率在相同样本下互为补数，不能重复加权。取消率、延误频率和延误后的严重程度也代表不同取舍。MVP 不设主观综合权重，而是让消费者按自己的偏好判断。

### 决策三：事实由程序算，AI 只做受约束解释

LLM 适合把结构化证据转成自然语言，但不适合作为事实数据库或唯一审计者。指标由确定性代码计算，AI 只能引用输入中存在的证据 ID，不能在自然语言中手写事实数字。

### 决策四：AI 复审不是最终门禁

第二次 DeepSeek 调用检查范围、证据支持、引用完整性、因果越界、限制项和建议语气。由于 AI 复审也可能出错，复审输出仍需满足固定 JSON 合同，最终由程序决定发布或降级。

### 决策五：当前不引入 RAG 或 Agent

当前输入是单份、结构固定且规模很小的证据 JSON，不存在跨文档检索问题；工作流步骤也是预先确定的，不需要模型自主选择工具。加入 RAG 或 Agent 会增加成本与失败面，不能直接提高当前事实可靠性。

## 4. 工作流与失败策略

1. 固定版本脚本下载数据并执行 SHA-256、字段和行数检查。
2. 确定性程序按统一口径计算结构化航司指标。
3. 若满足最低有效样本的航司少于两家，在模型调用前直接拒绝比较。
4. DeepSeek 根据证据生成消费者解释。
5. 确定性验证器检查结构、范围、证据 ID、自然语言数字、限制项和推荐强度。
6. 第二次 DeepSeek 调用做独立语义复审。
7. 程序验证复审合同；全部通过才发布解释，否则只展示已验证指标。

降级原则是“宁可少给结论，也不发布无法追溯或过度自信的建议”。

## 5. 验证证据

- 数据：固定 `nycflights13 1.0.2`；三张使用表的行数、字段和文件哈希已记录，重复运行 manifest 一致。
- 测试：12 项自动化测试通过，覆盖指标计算、比较范围、样本拒绝、无效证据 ID、自然语言手写数字、模型失败和复审不通过。
- 真实调用：使用 `deepseek-flash` 完成一次生成与一次独立复审，管线状态为 `approved`。
- 确定性复核：真实输出再次通过本地验证器。
- 隐私：API Key 仅保存在被忽略的 `.env`；公开审计明确记录 `api_key_recorded: false`。

运行证据见：

- `examples/jfk_lax_2013_carrier_comparison.json`
- `examples/deepseek_live/final_review.json`
- `examples/deepseek_live/ai_reviewer.json`
- `examples/deepseek_live/run_audit.json`

## 6. 示例洞察与表达边界

在 2013 全年 JFK 至 LAX 的示例中，五家航司均达到最低样本要求。Delta 在该范围内的到达延误率较低、到达准点率较高且延误航班平均延误时长较短；JetBlue 的取消率较低，但到达延误率较高。

正确表达是“在这一历史航线与日期范围内存在上述指标取舍”。不能表达为“Delta 是最好的航司”“JetBlue 更可靠”或“这些差异由航司管理导致”。

## 7. 成功标准与后续验证

本轮技术 MVP 的成功标准已经达到：数据可复现、指标可解释、输出可追溯、AI 失败可降级、真实模型调用可审计。

若继续做产品验证，优先级应是：

1. 用 5—8 名目标消费者访谈验证他们是否理解这些指标、是否会改变选择。
2. 测试“指标表”“AI 摘要”“按偏好排序”三种信息呈现方式的理解率和决策用时。
3. 接入更新且覆盖更广的数据后，再评估实时性、地区扩展和统计稳定性。
4. 有真实用户偏好证据后，才讨论个性化权重；仍不应把权重包装成客观真理。

## 8. 真实贡献边界

本项目受课程任务启发，但公开仓库在独立目录中重新定义问题、重新获取数据并实现。AI 协助文档与代码草稿、Prompt、测试设计、审查和排错；程铭负责产品定位、范围取舍、密钥安全配置、此前数据与分析批次的实际运行和结果核对，并决定发布边界。本次 DeepSeek 集成、真实调用与发布前检查由 AI 助手在本地项目中代为执行并留下审计证据，仍需程铭独立复跑与讲解验收。

这能证明已完成一次可审计 AI 产品工作流的设计、运行和验收，不等于已具备独立从零开发全部生产代码、完成真实航空业务上线或获得线上用户效果。
